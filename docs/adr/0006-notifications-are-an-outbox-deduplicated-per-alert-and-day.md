# Notifications are an outbox, deduplicated per alert and forecast day

The `evaluate` job compares active Alerts against Forecasts for today onward and inserts a Notification for each one that reaches its Threshold. It works through Locations that have Fields in batches (`EVALUATE_BATCH_SIZE`, 200 by default), one transaction per batch, so the Field and Alert locks, memory and query plan stay bounded per batch, and a Field update waits at most for the batch holding its Location. Its check for days already notified only looks at Notifications from today on, because the Notification table is never purged and would otherwise be scanned in full on every run. A database error in one batch is logged and counted, and the run carries on with the next batch, so one failing batch cannot keep the Locations after it from ever being evaluated; the failed batch is retried on the next run. The `notify` job then delivers pending Notifications to users, grouped into Messages. The two jobs coordinate only through the database (ADR-0002). The Notification table is the outbox itself: each row carries its delivery status (`pending`, `sent`, `failed`, `expired`) and an attempt count. There is no separate generic outbox table, and a Message is not persisted.

`notify` claims a batch of **users** that have at least one due Notification and no Message in flight, with `FOR UPDATE SKIP LOCKED` on the user, so two replicas never split one user's Notifications into two Messages. The batch size counts users. In the same transaction it reads all of each claimed user's pending Notifications, including ones still sitting out a retry backoff, and drops any user who no longer has one due or now has one leased: locking the user does not re-check the Notifications, so a run that read before another run's claim committed would otherwise send that user's in-flight Notifications again. That read skips locked rows instead of waiting: a row locked at that moment is being expired, withdrawn, deleted or recorded, and waiting would risk deadlocking with a pause or a Field move. Each user's Notifications are ordered by day and split into Messages of at most 20, sent one after another so the earliest days arrive first; different users are sent concurrently. The claim sets `leased_until` on every claimed row to twice the send time limit per Message of that user, and commits right away, so no lock is held while messages go over the network. A user with a leased Notification is not claimed again until the lease is cleared or ends, even if `evaluate` adds a new due Notification for them meanwhile; leased and backing-off rows are told apart by `leased_until`, while `next_attempt_at` holds only the backoff. A Message succeeds or fails as a whole, and its outcome is committed in its own transaction, so deleting an Alert never waits for a batch. A database error while recording one Message's outcome is logged and counted, the rest of the run carries on, and the lease brings those Notifications back later. The run keeps claiming batches while the last one came back full and produced at least one Message, so a backlog drains in one run, and users whose due rows are all locked by another transaction cannot keep it spinning. It claims only users that were due when it started, so a Message that fails waits for a later run instead of being retried in a loop. Delivery is at least once: a crash re-sends only the Messages that were in flight, once their lease has ended.

To prevent starvation, each run of `notify` first marks pending Notifications for past days as `expired`, and a Notification whose day ends after it is claimed is expired instead of sent. It then claims only users with a row whose `next_attempt_at` has passed, ordered by their earliest such day and then `next_attempt_at`, so the most urgent risk is sent first. A Message that fails with a transient error pushes `next_attempt_at` forward for all its Notifications with capped exponential backoff, using the highest attempt count among them, so they all share one retry time and a user that keeps failing sits out a delay and cannot fill every batch. There is no attempt limit: a transient failure is retried until the day has passed and the Notification expires, so a sender outage of a few hours does not lose that day's warnings. When the sender rejects a Message permanently (for example, the phone number no longer exists), all its Notifications become `failed` and are never retried.

An Alert produces at most one Notification per forecast day, enforced by a unique constraint on (alert, day). Evaluation inserts with `ON CONFLICT DO NOTHING`, so repeated or concurrent runs are idempotent. Later changes to that day's probability produce nothing: a rise from 55% to 90% is not reported, a drop below the Threshold is not reported, and neither is crossing the Threshold again. Editing a Threshold does not reset days that were already notified. Each Notification stores the probability and Threshold at the moment it fired, because the Forecast row keeps being overwritten by ingestion.

When a Field's coordinates change so that it moves to another Location, the pending Notifications of its Alerts are deleted in the same transaction as the Field update. They were created from the old Location's Forecast and would warn about the wrong place. Sent, expired and failed Notifications are kept, so the one-per-Alert-and-day rule still holds for those days, and the next `evaluate` run fills only the days not yet notified from the new Location's Forecasts. Renaming a Field, or moving it within the same Location, deletes nothing. `evaluate` reads Fields `FOR SHARE` in each batch, so a batch that overlaps a move either waits for it and uses the new Location, or commits first and has its pending Notifications deleted by the move. A Field that moves between batches into a Location already evaluated in that run is picked up by the next run.

Pausing an Alert deletes its pending Notifications, and raising its Threshold deletes the pending ones whose probability is now below it, in the same transaction as the Alert update. Lowering the Threshold or resuming deletes nothing, and the next `evaluate` run fills the missing days. Sent, expired and failed Notifications are kept here too. `evaluate` also reads Alerts `FOR SHARE`, so a run that overlaps a pause or a Threshold change either waits for it and sees the new values, or finishes first and has its pending Notifications withdrawn by the update.

## Considered Options

- **A separate `outbox_messages` table** written alongside the Notification. Rejected: a Notification is already "a record that is then delivered", and nothing else publishes messages yet.
- **A Notification on every threshold crossing.** Rejected: it needs stored state per Alert and day, and it repeats messages as the forecast moves around the Threshold.
- **A daily reminder per Alert while a forecast stays above the Threshold.** Rejected: it does not say which day is at risk, sends repeated messages for the same event across the 7-day horizon, and its key depends on the evaluation date's timezone.

## Consequences

Escalation and all-clear Notifications, if wanted later, are new kinds of Notification added on top of this key, not replacements for it. Notifications are deleted along with their Alert.
