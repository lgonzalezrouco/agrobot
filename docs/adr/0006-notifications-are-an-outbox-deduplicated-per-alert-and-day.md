# Notifications are an outbox, deduplicated per alert and forecast day

The Notification table is the outbox: `evaluate` inserts rows, `notify` delivers them to users grouped into Messages, and the two jobs coordinate only through the database (ADR-0002). Each row carries its delivery status (`pending`, `sent`, `failed`, `expired`) and an attempt count. There is no separate generic outbox table, and a Message is not persisted.

**One per Alert and day.** A unique constraint on (alert, day) plus `ON CONFLICT DO NOTHING` make repeated or concurrent `evaluate` runs idempotent. Later changes to that day's probability produce nothing: a rise from 55% to 90%, a drop below the Threshold and crossing it again are not reported, and editing a Threshold does not reset days already notified. Each Notification stores the probability and Threshold it fired with, because ingestion keeps overwriting the Forecast row.

**Evaluate.** `evaluate` compares active Alerts against Forecasts for today onward and inserts a Notification for each day that reaches the Alert's Threshold. It works through Locations that have Fields in batches (`EVALUATE_BATCH_SIZE`, 200 by default), one transaction per batch, so the Field and Alert locks, memory and query plan stay bounded, and a Field update waits at most for the batch holding its Location. The check for days already notified only reads Notifications from today on, because the table is never purged and would otherwise be scanned in full. A database error in a batch is logged and counted and the run carries on, so one failing batch cannot keep the Locations after it from being evaluated; the next run retries it.

**Claiming.** `notify` claims a batch of **users** (the batch size counts users) that have a due Notification and no Message in flight, with `FOR UPDATE SKIP LOCKED` on the user, so two replicas never split one user's Notifications into two Messages. It claims only users that were due when the run started, meaning a row whose `next_attempt_at` has passed, ordered by their earliest such day and then `next_attempt_at`: the most urgent risk goes first, and a failed Message waits for a later run instead of looping. In the same transaction it reads all of each user's pending Notifications, including ones sitting out a backoff, and drops any user who no longer has one due or now has one leased: locking the user does not re-check the Notifications, so a run that read before another run's claim committed would send that user's in-flight Notifications again. That read skips locked rows instead of waiting, because a locked row is being expired, withdrawn, deleted or recorded, and waiting could deadlock with a pause or a Field move. The claim sets `leased_until` on every claimed row to twice the send time limit for each of that user's Messages and commits at once, so no lock is held while messages go over the network. A leased user is not claimed again until the lease is cleared or ends, even if `evaluate` adds a new due Notification meanwhile. `leased_until` marks a lease; `next_attempt_at` holds only the backoff.

**Sending.** Each user's Notifications are ordered by day and split into Messages of at most 20, sent one after another so the earliest days arrive first; different users are sent concurrently. After a transient failure, that user's later Messages are not sent in this run: they wait for the same retry time, so later days never arrive before earlier ones. A Message succeeds or fails as a whole, and its outcome is committed in its own transaction, so deleting an Alert never waits for a batch. A database error recording an outcome is logged and counted, the run carries on, and the lease brings those Notifications back later. The run keeps claiming while the last batch came back full and produced at least one Message, so a backlog drains in one run, but users whose due rows are all locked elsewhere cannot keep it spinning. Delivery is at least once: a crash re-sends only the Messages in flight, once their lease ends.

**Retries and expiry.** Each run first marks pending Notifications for past days `expired`, and a Notification whose day ends after it is claimed is expired instead of sent. A transient failure pushes `next_attempt_at` forward for all of the Message's Notifications with capped exponential backoff, using their highest attempt count, so they share one retry time and a user that keeps failing sits out a delay instead of filling every batch. There is no attempt limit: retries go on until the day has passed and the Notification expires, so a sender outage of a few hours does not lose that day's warnings. A permanent rejection (for example, the phone number no longer exists) marks all of the Message's Notifications `failed`, never retried.

**Withdrawal.** In the same transaction as the update, moving a Field to another Location deletes the pending Notifications of its Alerts, since they came from the old Location's Forecast; pausing an Alert deletes its pending Notifications; and raising its Threshold deletes the pending ones now below it. Renaming a Field, moving it within its Location, lowering a Threshold or resuming an Alert deletes nothing. Sent, expired and failed Notifications are always kept, so the one-per-Alert-and-day rule still holds, and the next `evaluate` run fills only the missing days (after a move, from the new Location's Forecasts). `evaluate` reads Fields and Alerts `FOR SHARE`, so a batch that overlaps such an update either waits for it and sees the new values, or commits first and has its pending Notifications deleted by the update. A Field that moves between batches into a Location already evaluated in that run is picked up by the next run.

## Considered Options

- **A separate `outbox_messages` table** written alongside the Notification. Rejected: a Notification is already "a record that is then delivered", and nothing else publishes messages yet.
- **A Notification on every threshold crossing.** Rejected: it needs stored state per Alert and day, and repeats messages as the forecast moves around the Threshold.
- **A daily reminder per Alert while a forecast stays above the Threshold.** Rejected: it does not say which day is at risk, repeats messages for the same event across the 7-day horizon, and its key depends on the evaluation date's timezone.

## Consequences

Escalation and all-clear Notifications, if wanted later, are new kinds of Notification on top of this key, not replacements for it. Notifications are deleted along with their Alert.
